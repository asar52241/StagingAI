# Robokassa: ошибка 29 и подпись чека

## Актуальное исправление — 12 сентября 2026

На рабочем сайте создание заказа возвращало 200, но Robokassa отклоняла переход с кодом 29. Предыдущий вывод этого документа об исключении `Receipt` из подписи оказался неверным для текущего запроса.

Подпись должна учитывать **значение `Receipt`, которое Robokassa получает после разбора query-строки**. В текущей реализации это исходный компактный JSON. Он включается в MD5 без URL-кодирования, а при передаче в URL кодируется один раз:

```text
receiptJson = JSON.stringify(receipt)
SignatureValue = md5(MerchantLogin:OutSum:InvId:receiptJson:Пароль#1)
URL: ...&Receipt=encodeURIComponent(receiptJson)
```

Чек остаётся в запросе. Подписи уведомлений ResultURL и возврата SuccessURL используют свои прежние формулы без `Receipt`.

## Проверка на текущем магазине

Проверено в браузере с действующим тестовым паролем магазина, без проведения платежей:

| Данные в подписи | Передача Receipt в URL | Результат |
| --- | --- | --- |
| Без Receipt | JSON закодирован один раз | Ошибка 29 |
| Без Receipt | Receipt отсутствует | Демо-форма открывается; только диагностический вариант |
| Исходный JSON | JSON закодирован один раз | Демо-форма открывается — выбран этот вариант |
| URL-кодированный JSON | JSON закодирован один раз | Ошибка 29 |
| URL-кодированный JSON | JSON закодирован дважды | Демо-форма открывается |

Последний вариант тоже согласован: после транспортного декодирования сервер получает URL-кодированную строку, которая использовалась в подписи. Ошибка возникает при смешивании этих двух способов, когда подписывается одна строка, а сервер получает другую.

Официальные источники: [сборка подписи](https://docs.robokassa.ru/ru/pay-interface), [фискализация](https://docs.robokassa.ru/ru/fiscalization). Пример HTML-формы в документации предварительно кодирует JSON; браузер затем выполняет транспортное кодирование поля формы. Его нельзя напрямую переносить в GET-ссылку с одним слоем кодирования без изменения подписываемого значения.

## Регрессионные проверки

`tests/robokassa.test.ts` и `tests/security.test.ts` проверяют подпись по фактически полученному значению `Receipt`, включая кириллицу, пробелы и амперсанд, сумму заказа и фиксированный домен возврата. Локальные пароли не заменяют рабочие: при диагностике установлено, что локальный тестовый пароль отличается от действующего в Vercel.
