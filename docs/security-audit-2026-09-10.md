# Аудит и исправления StagingAI

Проверка рабочей копии: 9–10 сентября 2026 года. Просмотрены маршруты приложения, все четыре API, платёжные и браузерные библиотеки, редактор масок, UI-компоненты, конфигурация, зависимости и HTML-прототип. Исходные пользовательские изменения в событиях Метрики сохранены. Рекламные материалы и локальные секреты не изменялись.

Последующее изменение: Redis заменён на PostgreSQL (Neon) по выбору владельца проекта. Условия настройки ниже обновлены; исходные результаты аудита относятся к первоначальной проверке.

## Исправленные проблемы

| Проблема до исправления | Последствие | Изменение |
|---|---|---|

| Лимит по произвольному `X-Forwarded-For`, бесконечно растущая Map | Обход ограничения и расход памяти | Только явно доверенный proxy-header; общее атомарное хранилище с TTL, ограниченный development store |
| Multipart полностью читался до ограничения размера файлов | Избыточное потребление памяти/долгие загрузки | Ограничение байтов потока до multipart, включая запросы без Content-Length, таймаут чтения, предел размеров изображения |
| SDK повторял запросы, а ошибки провайдера возвращались дословно | Лишние оплаченные попытки и раскрытие деталей | `maxRetries: 0`, таймаут, нейтральные ошибки и безопасные имена файлов |

| Подпись платежа попадала в URL Метрики, логировался полный XML | Передача платёжных параметров и данных провайдера | Фильтрация URL, no-referrer, отключённый Webvisor, удаление полного XML и исходных IP из прикладных логов |

| Дублирование восстановления, ошибки теряли pending, повторная попытка недоступна при ошибке | Потеря заказа, повторные генерации и невозможность повторить сбой | Единый путь восстановления, сохранение прогресса, явный retry, восстановление отмены без InvId, новый заказ |

MD5 сохранён только для протокола Robokassa, который использует алгоритм из настроек магазина. Собственные токены приложения используют отдельный секрет и HMAC-SHA256; подписи сравниваются через `timingSafeEqual`.

## Условия выкладки и ограничения

### Проверка перехода на Neon

- `npm test` — 61 проверка успешно, включая выполнение настоящего SQL в PGlite: конкурентная запись, лимиты заказа, повторная оплата, срок действия, ограниченная очистка и параметризация.
- Таблица `public.stagingai_records` и индекс срока созданы в предоставленном Neon. Через реальное HTTPS-подключение проверены чтение, единственный победитель из 12 конкурентных вставок/обновлений, сохранение всех 8 одновременных приращений и отказ устаревшей записи после истечения срока. Все временные проверочные записи удалены.
- `npm run typecheck`, production build в копии без `#` и `git diff --check` — успешно. Установка новых зависимостей завершилась с 0 известных уязвимостей npm audit.
- Пароль подключения не записывался в исходники или Git. После передачи пароля в переписке требуется его ротация и проверка обновления `DATABASE_URL` в Vercel перед выкладкой.
- Обновлённый код в Vercel не выкладывался. Реальные платежи и вызовы генерации при этой проверке не выполнялись.

### Настройки и ограничения

1. Обязательны `DATABASE_URL` (PostgreSQL/Neon), таблица из `db/001_order_store.sql` и случайный `PAYMENT_TOKEN_SECRET` длиной не менее 32 символов. Подготовка таблицы: `npm run db:setup`. Без базы production отвечает ошибкой, а не разрешает обработку. Redis и переменные Upstash больше не используются.
2. Нужны правильный `NEXT_PUBLIC_SITE_URL`, MD5 в настройках магазина, ResultURL и GET-адреса возврата. Реальные платежи и платные генерации при аудите не выполнялись; провайдеры в тестах подменены.
3. Старые MD5-cookie и счета, отсутствующие в новом хранилище, больше не принимаются. Перед переходом завершите активные старые заказы либо обеспечьте ручное выполнение. Автоматическая небезопасная миграция старых bearer-токенов не добавлена.
4. Одинаковые байты исходного изображения делят один лимит из двух попыток. Вызов провайдера считается попыткой даже при его ошибке/таймауте: нельзя достоверно исключить начисление стоимости. Возврат попытки после неопределённой ошибки не выполняется автоматически.
5. Фото остаются в браузере, а не в PostgreSQL. После удаления данных сайта восстановить их нельзя. Новые/повторные checkout одного браузера используют одну pending-cookie; завершённая оплата имеет отдельную cookie. Без учётной записи доступ между разными браузерами не переносится.
6. Пределы reverse proxy, настройки Robokassa, реальные платёжные возвраты и инфраструктура production не проверялись. Полнота защиты от DoS зависит также от хостинга. Проверка исходников и тесты не доказывают отсутствие всех возможных уязвимостей.

## Основания внешних изменений

Исправленная версия Next.js выбрана по [официальному выпуску безопасности от 25 августа 2026](https://nextjs.org/blog/august-2026-security-release); ветка 14 отсутствует среди поддерживаемых в [политике поддержки](https://nextjs.org/support-policy).

Правила подписи и дополнительных адресов возврата сверены с [документацией Robokassa](https://docs.robokassa.ru/ru/notifications-and-redirects), а различие `IncSum` / `OutSum` и код успешной операции — с [XML-интерфейсом](https://docs.robokassa.ru/ru/xml-interfaces).

Атомарное сохранение использует [PostgreSQL `INSERT … ON CONFLICT` и условный `UPDATE`](https://www.postgresql.org/docs/current/sql-insert.html) через [HTTPS-драйвер Neon](https://github.com/neondatabase/serverless). Срок записи проверяется по часам базы. Просроченные записи не дают доступ; их физическая очистка выполняется ограниченными порциями при последующих записях, без фоновых задач, которые Vercel может остановить.
