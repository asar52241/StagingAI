# Аудит и исправления StagingAI

Проверка рабочей копии: 9–10 сентября 2026 года. Просмотрены маршруты приложения, все четыре API, платёжные и браузерные библиотеки, редактор масок, UI-компоненты, конфигурация, зависимости и HTML-прототип. Исходные пользовательские изменения в событиях Метрики сохранены. Рекламные материалы и локальные секреты не изменялись.

## Исправленные проблемы

| Проблема до исправления | Последствие | Изменение |
|---|---|---|
| `/api/declutter` проверял подпись cookie, но не расходовал `count` | Неограниченное число платных генераций после одной оплаты | Серверные заказы, атомарные резервации, лимит источников и две попытки на источник; параллельные запросы не обходят лимит |
| Срок действия был только атрибутом cookie | Скопированный токен можно было отправлять после истечения срока браузерной cookie | HMAC-SHA256, проверяемый сервером срок, разделение токенов заказа и оплаты |
| Повторная проверка оплаты выдавала новый доступ без состояния заказа | Повторное использование платежа | Подтверждение идемпотентно, остаток и срок не сбрасываются |
| `noSig=true` в тестовом режиме обходил подпись | Бесплатное подтверждение оплаты | В тесте обязательна корректная подпись или сохранённое подписанное уведомление |
| Для восстановления достаточно было номера счёта | Доступ к чужой оплате при знании/подборе номера | Проверка случайного секрета владельца из HttpOnly cookie |
| ResultURL только отвечал `OK`, не сохраняя оплату | Нет надёжного подтверждения и восстановления | Сначала сохранение, затем ответ; ошибка хранилища даёт 503 для повторного уведомления |
| При отсутствии суммы в XML использовалась сумма запроса; использовался `IncSum`, округление и минимум | Неверное количество оплаченных фото | Точное сравнение сохранённой суммы с `Info.OutSum`; отсутствие/повтор суммы и недоплата отвергаются |
| Нормализация суммы до проверки подписи | Корректные подписи могли не проходить | Подпись проверяется по исходной строке, десятичная сумма отдельно переводится в копейки |
| Неограниченный/дробный `photoCount`, необработанный JSON | Неверные счета и ошибки 500 | Строгие целые 3–30, ограничение тела, контролируемые ответы |
| Возврат строился из `x-forwarded-host` / `x-forwarded-proto` | Подмена адреса возврата | Настроенный домен, подписанные `SuccessUrl2`/`FailUrl2` |
| Лимит по произвольному `X-Forwarded-For`, бесконечно растущая Map | Обход ограничения и расход памяти | Только явно доверенный proxy-header; общее атомарное хранилище с TTL, ограниченный development store |
| Multipart полностью читался до ограничения размера файлов | Избыточное потребление памяти/долгие загрузки | Ограничение байтов потока до multipart, включая запросы без Content-Length, таймаут чтения, предел размеров изображения |
| SDK повторял запросы, а ошибки провайдера возвращались дословно | Лишние оплаченные попытки и раскрытие деталей | `maxRetries: 0`, таймаут, нейтральные ошибки и безопасные имена файлов |
| Ветка результата загружала произвольный URL | Излишняя поверхность исходящих запросов | Для выбранной модели принимается только результат base64 |
| Подпись платежа попадала в URL Метрики, логировался полный XML | Передача платёжных параметров и данных провайдера | Фильтрация URL, no-referrer, отключённый Webvisor, удаление полного XML и исходных IP из прикладных логов |
| WebP/GIF принимались UI, но не парсером сервера | Ошибки обработки после оплаты | Нормализация всех входных изображений в браузере в PNG/JPEG с удалением метаданных |
| Калькулятор давал скидку, checkout считал по 50 ₽ за фото | Например, обещанные 450 ₽ за 10 фото превращались в 500 ₽ | Единый расчёт с уже рекламировавшимися пакетами для лендинга, студии, сервера и ecommerce |
| Дублирование восстановления, ошибки теряли pending, повторная попытка недоступна при ошибке | Потеря заказа, повторные генерации и невозможность повторить сбой | Единый путь восстановления, сохранение прогресса, явный retry, восстановление отмены без InvId, новый заказ |
| История масок хранила полные RGBA-снимки | До 756 MB на 21 снимок 3000×3000 | Только alpha, лимит истории 96 MiB, очистка временных URL и защита от устаревших загрузок |
| Пустой список в AccordionFeatureSection, HTML-интерполяция имени файла в прототипе | Падение компонента / локальная HTML-инъекция | Безопасное пустое состояние, единый выбранный элемент, экранирование имени |
| Уязвимые версии зависимостей | Известные проблемы Next.js и транзитивных пакетов | Next.js 15.5.24; исправленные транзитивные пакеты, явное переопределение PostCSS для Next.js |

MD5 сохранён только для протокола Robokassa, который использует алгоритм из настроек магазина. Собственные токены приложения используют отдельный секрет и HMAC-SHA256; подписи сравниваются через `timingSafeEqual`.

- `npm test` — 53 проверки, включая параллельные резервации, повторные уведомления, подделку/истечение токенов, тестовый обход, реальные правила XML на подставных ответах, недоплату, скидки, некорректные изображения и ограничения потоков.

- Production build проходит в временной копии с путём без `#`. В исходном пути `####` сохраняется проблема Webpack/tracing, ранее описанная в README. Проверочная копия не содержит `.env.local`.
- `git diff --check` — успешно. Поиск типовых открытых ключей/закрытых ключей в отслеживаемых файлах совпадений не обнаружил; это не проверка истории Git и не универсальный поиск секретов.

## Условия выкладки и ограничения

1. Обязательны `UPSTASH_REDIS_REST_URL`, `UPSTASH_REDIS_REST_TOKEN` и случайный `PAYMENT_TOKEN_SECRET` длиной не менее 32 символов. Redis должен сохранять состояние и не вытеснять записи. Без него production отвечает ошибкой, а не разрешает обработку. Внешняя база в этой сессии не создавалась и не подключалась; успешная работа адаптера с реальным Redis ещё требует проверки в окружении выкладки.
2. Нужны правильный `NEXT_PUBLIC_SITE_URL`, MD5 в настройках магазина, ResultURL и GET-адреса возврата. Реальные платежи и платные генерации при аудите не выполнялись; провайдеры в тестах подменены.
3. Старые MD5-cookie и счета, отсутствующие в новом хранилище, больше не принимаются. Перед переходом завершите активные старые заказы либо обеспечьте ручное выполнение. Автоматическая небезопасная миграция старых bearer-токенов не добавлена.
4. Одинаковые байты исходного изображения делят один лимит из двух попыток. Вызов провайдера считается попыткой даже при его ошибке/таймауте: нельзя достоверно исключить начисление стоимости. Возврат попытки после неопределённой ошибки не выполняется автоматически.
5. Фото остаются в браузере, а не в Redis. После удаления данных сайта восстановить их нельзя. Новые/повторные checkout одного браузера используют одну pending-cookie; завершённая оплата имеет отдельную cookie. Без учётной записи доступ между разными браузерами не переносится.
6. Пределы reverse proxy, доступность Redis, настройки Robokassa, реальные платёжные возвраты и инфраструктура production не проверялись. Полнота защиты от DoS зависит также от хостинга. Проверка исходников и тесты не доказывают отсутствие всех возможных уязвимостей.

## Основания внешних изменений

Исправленная версия Next.js выбрана по [официальному выпуску безопасности от 25 августа 2026](https://nextjs.org/blog/august-2026-security-release); ветка 14 отсутствует среди поддерживаемых в [политике поддержки](https://nextjs.org/support-policy).

Правила подписи и дополнительных адресов возврата сверены с [документацией Robokassa](https://docs.robokassa.ru/ru/notifications-and-redirects), а различие `IncSum` / `OutSum` и код успешной операции — с [XML-интерфейсом](https://docs.robokassa.ru/ru/xml-interfaces).

Атомарное сохранение использует Redis `EVAL` и условную запись через [REST API Upstash](https://upstash.com/docs/redis/features/restapi).
